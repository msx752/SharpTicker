# Migrating to SharpTicker

> [!IMPORTANT]
> **Versions: TickerQ `10.4.0` → the latest SharpTicker `1.x`.**
>
> - SharpTicker 1.0.0 corresponds to TickerQ 10.4.0, the last release published under MIT/Apache-2.0, plus the changes merged after it up to the base commit described in the [README](README.md#origin).
> - **On TickerQ 10.4.0:** follow this guide and install the latest 1.x release. A stop at 1.0.0 is not needed, and fixes are made on the latest release only.
> - **On an older TickerQ version:** first upgrade to TickerQ 10.4.0 and deploy it, using that project's own upgrade notes, then follow this guide. The two steps stay separate, so each one can be checked on its own.
> - **On TickerQ 10.5.0 or later:** those releases are under a different license and are not covered. SharpTicker contains no code from them, and moving back was not tried.
> - Use **the same version for every SharpTicker package**.
> - You skip the releases after 1.0.0 in one step, so also read [Upgrading](docs/guide/upgrading.md): it lists what changed in each of them.

This guide moves an application from TickerQ to SharpTicker. 1.0.0 is the release built to match its origin; the releases after it changed behaviour, and this guide goes to the latest of them in one step.

There is a ready-to-use [prompt for AI coding assistants](#ai-assisted-migration) at the end of this page.

## What was run

The switch from the 10.4.0 packages to SharpTicker 1.4.0 was run on 2026-11-12, on .NET 10. One application was built twice, before and after the rename in this guide, and both builds used the same store one after the other:

- **EF Core with PostgreSQL**, with migrations generated by the old package: three runs. The old application was stopped; it ended without a stop while a job ran; and the same with the new application under another `NodeIdentifier`.
- **Redis as the job store**: four runs. Old application stopped, new one under the same `NodeIdentifier` and the default `InstanceName`; old application ended without a stop, new one under the same name and the default prefix; ended without a stop, another name and the old prefix; ended without a stop, another name and the default prefix. `NodeHeartbeatInterval` was 5 seconds. The first of these was run once more on 2026-11-13 with a build that has the fix for [#144](https://github.com/msx752/SharpTicker/issues/144), which is not in 1.4.0.

Not run:

- Old and new instances at the same time; see [Switching instances](#switching-instances).
- Other databases than PostgreSQL.
- .NET 8 and 9. The 10.4.0 packages target .NET 10 only; change the target framework in a deployment of its own.
- MongoDB. There is no 10.4.0 release of the MongoDB package on nuget.org, so a switch with stored MongoDB data was not run and is not covered.

Before that, the switch to 1.0.0 was checked against a real application on TickerQ 10.4.0 and against EF Core migrations generated with the old package.

## No database changes

Coming from TickerQ 10.4.0, the switch is a code and package change: it needs no change to the database schema and no data migration. The identifiers in storage are the same as before:

| Stored data | Identifier | Changed? |
|---|---|---|
| EF Core schema, tables, columns | schema `ticker`; `TimeTickers`, `CronTickers`, `CronTickerOccurrences` | No |
| MongoDB collections and indexes | prefix `ticker_` | No |
| Redis job store keys | `tq:tt:*`, `tq:cron:*`, `tq:co:*` | No; 1.3.0 and 1.4.0 added keys next to them |
| Crons seeded from code | `InitIdentifier` = `MemoryTicker_Seeded_<function>` | No |
| Jobs | function names, cron expressions, request payloads, retries, history | No |

Some stored jobs are handled differently after the switch. The two sections below say what the runs showed; read the one for your store before you switch.

## What happens to stored jobs with EF Core

In the three runs:

- Time jobs that were still waiting ran once each under the new version, with their retries and their request payloads. Chains ran by their run conditions: children that matched ran once, the others were recorded as `Skipped`.
- Rows that had ended under the old version kept their status, times and retry count.
- The cron seeded from code and a cron added through the API kept their ids and went on. No time slot got a second occurrence.
- No migration was applied, and the check in [Existing migrations](#existing-migrations) produced an empty migration.

Three things to act on:

- **Start the new version under the `NodeIdentifier` the old one used.** A job that was `InProgress` when the old application ended without a stop was released and started a second time when the new one started under the same name. Under another name it stayed `InProgress`. The default name is the machine name, which changes with every new container; see [Instance names](docs/guide/operations.md#instance-names).
- **Chain children that were left `Idle`.** A child without a time of its own whose parent has ended is run or skipped by the first fallback pass of the new version, however old it is. In two runs, a child that was running when the old application ended, with its row still `Idle`, was started a second time by the new version. Delete the ones you do not want to run before you switch.
- **Copies of a cron seeded from code.** When the store holds the cron of one `[TickerFunction]` more than once, the first start removes the copies with their occurrence history and keeps the oldest; only rows that carry the seed's `InitIdentifier` count. It logs a warning that names the function. This was run once, with a copy inserted by hand.

## What happens to stored jobs with Redis

In the four runs, crons kept their ids and went on, and time jobs that were still waiting ran once each under the new version. Two kinds of stored jobs did not carry over:

- **Time jobs the old version had already picked up.** In these runs, with the 10.4.0 packages, every time job that became due was set to `InProgress` and had not run when the old application ended, between 15 and 36 seconds later; its log has `Failed to deserialize JSON payload as TimeTickerEntity` for them. In the run with a stop, the stop did not release them. The new version logs the same warning for these rows and cannot read them as they are:
  - Started under the same `NodeIdentifier` (with the default `InstanceName`), it left them `InProgress`. In the run with the fix for #144 the new version read these rows: it released them when it started, logged no such warning, and each of them ran once, late.
  - Started under another `NodeIdentifier` with the old `InstanceName` (`tickerq:`), it released them once the heartbeat of the old instance had been missing for its confirmation time, about a minute after its start with the 5-second heartbeat of the run, and each of them ran once, about two and a half minutes late. With the default heartbeat of one minute the release takes about two heartbeat TTLs; see [When an instance stops](docs/guide/operations.md#when-an-instance-stops). This way was run once, after the old application had ended without a stop.
  - Started under another `NodeIdentifier` with the default `InstanceName`, it left them `InProgress`.
- **Children of chains the old version stored.** Their parents ran under the new version; the children and grandchildren stayed `Idle` and did not run, in all four runs.

So before you switch a Redis store, look at the time jobs that are `InProgress` and at the chains whose children have not run yet. For the `InProgress` jobs on 1.4.0, decide between the second way above and deleting them and adding them again after the switch. A version with the fix for #144 runs them after the switch under the same name, so delete the ones that should not run any more before you switch. For the chains, only deleting them and adding them again ran their children.

## Switching instances

Stop every old instance before the first new one starts. Old and new instances at the same time were not run for this guide.

They read and write the same tables and keys, but they do not guard each other's jobs. From the code and the 1.3.0 release notes, not from a run: if both kinds run at the same time anyway, expect at least this, for as long as an old instance is running:

- A job can run twice: an old instance can overwrite a claim a new one made.
- With Redis, a cron slot can run twice: an old instance creates cron occurrences the new ones do not see as the same slot.
- With Redis, an old instance leaves rows that 1.4.0 cannot read, as the runs above showed.
- With Redis, an old instance does not run the children of a chain that a new instance added. With EF Core, an old instance hands out a delayed child without waiting for its parent.

What [Running in production](docs/guide/operations.md#several-instances) describes applies once the last old instance is gone.

**Redis `InstanceName`.** Redis keeps which instances are alive under this prefix, and that is how jobs held by an instance that ended are released by another one. Its default changed from `tickerq:` to `sharpticker:`, so with the default a new instance does not see what the old ones wrote there. To keep the old prefix:

```csharp
opt.AddStackExchangeRedis(redis =>
{
    redis.Configuration = "localhost:6379";
    redis.InstanceName = "tickerq:"; // the 10.4.0 default
});
```

You can keep this setting permanently, or remove it in a later deployment once nothing an old instance held is left.

## 1. Packages

Replace each package with its counterpart and use the same version for all of them, the latest release:

| TickerQ | SharpTicker |
|---|---|
| `TickerQ` | `SharpTicker` |
| `TickerQ.Utilities` | `SharpTicker.Utilities` |
| `TickerQ.EntityFrameworkCore` | `SharpTicker.EntityFrameworkCore` |
| `TickerQ.MongoDB` | `SharpTicker.MongoDB` |
| `TickerQ.Caching.StackExchangeRedis` | `SharpTicker.Caching.StackExchangeRedis` |
| `TickerQ.Dashboard` | `SharpTicker.Dashboard` |
| `TickerQ.Instrumentation.OpenTelemetry` | `SharpTicker.Instrumentation.OpenTelemetry` |

```bash
dotnet add package SharpTicker
dotnet add package SharpTicker.EntityFrameworkCore
dotnet add package SharpTicker.Dashboard
```

Without a version, `dotnet add package` takes the latest release. The MongoDB row is the name mapping only; see [What was run](#what-was-run).

There is one package version for .NET 8, 9 and 10; there are no separate version lines per .NET release.

## 2. Code

Namespaces and every type or member whose name contains the product name change from `TickerQ` to `SharpTicker`. Everything else keeps its name.

| Before | After |
|---|---|
| `using TickerQ;`, `using TickerQ.Utilities...;`, ... | `using SharpTicker;`, `using SharpTicker.Utilities...;`, ... |
| `services.AddTickerQ(...)` / `app.UseTickerQ()` | `services.AddSharpTicker(...)` / `app.UseSharpTicker()` |
| `UseTickerQDbContext<TickerQDbContext>(...)` | `UseSharpTickerDbContext<SharpTickerDbContext>(...)` |
| `TickerQEfCoreOptionBuilder` | `SharpTickerEfCoreOptionBuilder` |
| `UseTickerQMongoClient(...)`, `TickerQMongoOptionBuilder` | `UseSharpTickerMongoClient(...)`, `SharpTickerMongoOptionBuilder` |
| `TickerQRedisOptionBuilder`, `TickerQRedisContext` | `SharpTickerRedisOptionBuilder`, `SharpTickerRedisContext` |
| `ITickerQHostScheduler`, `ITickerQDispatcher`, `ITickerQInstrumentation` | `ISharpTickerHostScheduler`, `ISharpTickerDispatcher`, `ISharpTickerInstrumentation` |
| `TickerQStartMode`, `TickerQConstructorAttribute`, `AddTickerQDiscovery(...)` | `SharpTickerStartMode`, `SharpTickerConstructorAttribute`, `AddSharpTickerDiscovery(...)` |

Unchanged names you keep using as they are: `TimeTickerEntity`, `CronTickerEntity`, `ITimeTickerManager<T>`, `ICronTickerManager<T>`, `TickerFunctionAttribute`, `TickerFunctionContext`, `TickerStatus`, `AddOperationalStore`, `AddDashboard`, `SetBasePath`, `SetSchema`, `UseApplicationDbContext` and the other members without the product name.

> [!WARNING]
> **Do not replace the text `TickerQ` everywhere.** Several unrelated names contain the same letters followed by "uery": `ITickerQueryable`, `TimeTickerQueryFilter`, `CronTickerQueryFilter`, `TickerQueryableExtensions`, `EfTickerQueryable`, `MongoTickerQueryable`, `InMemoryTickerQueryable`, `TickerQueryExtensions`. A blind replace turns `ITickerQueryable` into `ISharpTickerueryable`.
>
> Replace only where `TickerQ` is not followed by a lowercase letter. With a regular expression: find `TickerQ(?![a-z])`, replace with `SharpTicker`.

Only touch C# code and project files with that rule. Configuration keys, connection string names and database names belong to your application; see [step 6](#6-your-own-names-optional).

## 3. Entity Framework Core

### Registration

```csharp
// Before
opt.AddOperationalStore(ef =>
{
    ef.UseTickerQDbContext<TickerQDbContext>(db => db.UseNpgsql(connectionString));
    ef.SetSchema("ticker");
});

// After
opt.AddOperationalStore(ef =>
{
    ef.UseSharpTickerDbContext<SharpTickerDbContext>(db => db.UseNpgsql(connectionString));
    ef.SetSchema("ticker");
});
```

If you map the tickers into your own `DbContext` with `UseApplicationDbContext<TContext>(...)`, only the `using` lines change.

### Existing migrations

Your existing migrations and the model snapshot refer to the entities by their old type names as strings, for example `modelBuilder.Entity("TickerQ.Utilities.Entities.CronTickerEntity", ...)`. That is expected and safe:

- **Do not edit the `Up`/`Down` methods of existing migrations.** The old type-name strings in `*.Designer.cs` files and in the snapshot compile as they are.
- If a migration file has a `using TickerQ...;` line, change it to `using SharpTicker...;` so it compiles. With the packaged context, the `*.Designer.cs` files and the snapshot also name it in `[DbContext(typeof(TickerQDbContext))]`; change that to `SharpTickerDbContext`.
- EF Core compares tables and columns, not .NET type names. The next `dotnet ef migrations add` rewrites the snapshot with the new names and contains **no table changes**.

**You do not need to add or apply a migration for the switch.** If you want to confirm it, run this once after switching; it does not touch the database:

```bash
dotnet ef migrations add VerifySharpTicker
```

- Snapshot generated with TickerQ 10.4.0: the migration is **empty**. Remove it with `dotnet ef migrations remove`, or keep it to record the new type names in the snapshot.
- Snapshot generated with an older TickerQ version: the migration may add the `IsEnabled` and `IsSystemPaused` columns to `CronTickers`. That comes from the 10.4.0 schema, not from the rename. **Before you apply it, edit the generated `AddColumn` for `IsEnabled` so that existing rows stay enabled:** change `defaultValue: false` to `defaultValue: true`. EF writes `false` because the column has no store default, so applied as generated, every existing cron is disabled and the scheduler skips it. If you already applied it, run `UPDATE` on `CronTickers` to set `IsEnabled` to true (check first that none of the crons were paused on purpose).
- **Stop if the migration drops, renames or creates any `ticker` table or column other than those two.** That means something else changed, for example the schema name or a custom configuration.

If you create the schema with `EnsureCreated()` or `GenerateCreateScript()` instead of migrations, the generated schema is identical.

`CronTickerEntity.IsSystemPaused` is still mapped so existing databases need no change, but it is marked `[Obsolete]` and is no longer used. Pause a cron with `IsEnabled`.

## 4. Runtime differences

| Area | Before | After | Action |
|---|---|---|---|
| Dashboard default path | `/tickerq/dashboard` | `/ticker/dashboard` | Only if you relied on the default. An explicit `SetBasePath(...)` keeps working; `SetBasePath("/tickerq/dashboard")` keeps the old URL. |
| Redis coordination prefix (`InstanceName`) | `tickerq:` | `sharpticker:` | See [Switching instances](#switching-instances) and, for what it changes for stored jobs, [What happens to stored jobs with Redis](#what-happens-to-stored-jobs-with-redis). Job data keys (`tq:*`) are unchanged. |
| Tracing | ActivitySource `TickerQ`, tags `tickerq.*` | ActivitySource `SharpTicker`, tags `sharpticker.*` | Update OpenTelemetry source names, dashboards and alerts that filter on the old names. |
| Generated code | `TickerQInstanceFactory` | `SharpTickerInstanceFactory` | Only if your code refers to the generated class by name. |
| Source generator diagnostics | `TQ001` to `TQ011` | `ST001` to `ST011`, same numbers and meanings | Update `NoWarn`, `.editorconfig` and `#pragma` lines that name the old ids. |

## 5. Removed APIs

The integration with the hosted Hub (RemoteExecutor and SDK packages) is not part of SharpTicker. The members that only served it are removed:

- `SdkOfflineSkipException`
- `TickerFunctionProvider.MergeRemoteFunctions`, `MergeRemoteRequestInfo`, `ReplaceFunctions`, `ReplaceRequestInfo`, `FunctionNodeResolver`, `ResolveNodeName`
- `ITickerDashboardDataService.GetNodesAsync`, `GetNodeFunctionsAsync`, `GetNodeJobsAsync`, and the `NodeDto` and `NodeHealthStatus` types
- `CronTickerFlatDto.IsSystemPaused`

Running several instances of your application against one store does not need any of them; it works through the shared database or Redis as before.

## 6. Your own names (optional)

Configuration keys, connection string names, environment variables and database names are your application's, not the library's. Nothing requires you to rename them.

If you do rename them, keep reading the old name for a while. A missing connection string often falls back to a default, so a renamed key that is not yet set on a server can silently point the scheduler at the wrong database:

```csharp
var schedulerConnection =
    builder.Configuration.GetConnectionString("SharpTicker")
    ?? builder.Configuration.GetConnectionString("TickerQ"); // old name, remove once every environment is updated
```

Never rename the database itself as part of this migration.

## 7. Checklist

- [ ] Every `TickerQ*` package is replaced by its `SharpTicker*` counterpart, all on the same version.
- [ ] The solution builds, and no project references a `TickerQ*` package, directly or transitively.
- [ ] Your tests pass.
- [ ] EF Core: `dotnet ef migrations add VerifySharpTicker` is empty, or only adds `IsEnabled`/`IsSystemPaused` (with `IsEnabled` set to `defaultValue: true`, see above).
- [ ] The dashboard opens at the expected URL.
- [ ] Tracing dashboards and alerts use the `SharpTicker` source and `sharpticker.*` names.
- [ ] EF Core: the new version runs under the `NodeIdentifier` the old one used.
- [ ] Existing cron jobs fire and their history shows in the dashboard.
- [ ] No time job is left `InProgress` from before the switch. Redis: no chain from before the switch is left with children that did not run.
